- [ ] `card_price_history` read-path: the movers attribution work (`portfolioMovers.repository.ts`) needs "closest row at-or-before a target date" for a card set, and even with the right index (`card_price_history_card_date`, confirmed via `EXPLAIN`) that's ~9.8:1 fetched-to-kept rows for any single query, because it has to read the whole lookback window (e.g. 10 days) per card just to keep the newest row — table bloat is NOT the cause (0.088% dead tuples, confirmed via `pg_stat_user_tables`). CORRECTION: an earlier version of this entry assumed "intraday" (same-day) duplicate rows were the culprit — wrong; the table's unique constraint `(card_id, source, variant, grade, snapshot_date)` already forbids more than one row per day per combo, so there's nothing same-day to dedupe. The actual fix is a small, nightly-maintained rollup table scoped to the recent window only (~35-40 days, all cards) — small enough to stay cache-resident regardless of the fetch ratio, unlike querying the full 17M-row table directly. Durable fast-follow to the LATERAL-rewrite fix shipped in the movers feature itself.
- [ ] `card_price_history` unbounded growth: ~17M rows, no retention policy, ~1 row/card/source/variant/grade/day, no pruning ever run. A SEPARATE concern from the read-path item above — pruning old (e.g. >90d) history shrinks total table/index size and disk/backup cost, but does NOT by itself fix the read-path's fetched-to-kept ratio for a *recent* lookback window (a 10-day-wide query re-reads the same ~10 days regardless of how much older history exists behind it). Needs its own real retention policy on the source table.

Found while scoping the PriceCharting sync demand set (2026-08-25) — 0/107 is a real product finding beyond that pipeline.
